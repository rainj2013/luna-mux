# Luna Mux AI 协作开发规范

## 目的与适用范围

本规范是高风险变更的完整流程，用于跨模块功能、共享契约、持久化、进程生命周期、安全边界和平台适配。文档、样式和不影响共享状态的局部修改走 `AGENTS.md` 中的快速流程，无需读取或执行本文其余部分。

规范的基本原则是：先建立可检查的架构假设，再让 AI 实现；以测试和差异检查作为证据；让独立上下文重新审视风险。AI 生成的代码与人工代码遵循同一合并标准。

## 1. 变更分级

开始工作前先判断变更级别。L0/L1 走快速流程；L2/L3 才执行本文后续章节：

| 级别 | 典型范围 | 最低验证 |
| --- | --- | --- |
| L0 文档/样式 | docs、文案、纯 CSS、无行为变化 | 检查 diff；必要时 `npm run web:build` |
| L1 局部行为 | 单个组件、纯函数、非共享 UI 状态 | 最窄相关检查或测试；通常为 `npm run typecheck` |
| L2 共享契约 | 原生命令接口、共享服务或状态、Runtime/Control contract、持久化格式、MCP/Hook 契约 | `npm run check`、`npm test`、相关 contract/native-core 测试 |
| L3 运行时/平台 | 改变进程生命周期、权限边界、平台适配、PTY/SSH/SFTP 或浏览器后端行为 | L2 全部验证 + 端到端场景 + 受影响平台实机验证 |

按行为和影响范围分级，不因修改某个 Rust 文件或浏览器组件就自动升级。涉及共享调用、持久化格式、公共 JSON、进程生命周期或安全边界时至少按 L2 处理；影响尚不明确时，先核查相关调用链。

## 2. L2/L3 开工前：写清架构验收条件

用简短计划说明与本次变更相关的事项，无需为不相关项逐项填表：

1. **边界**：需求属于哪一层，允许修改哪些模块？
2. **数据归属**：会话、窗格、Runtime、连接、Agent、传输和隧道等状态由哪个 manager/database/contract 负责？新增状态的唯一事实来源是什么？
3. **调用链**：用户操作或 Agent 请求如何经过 React → Tauri command → service/backend → 外部进程，并通过什么事件或返回值回到 UI？错误在哪里转换和记录？
4. **兼容性**：旧 API、JSON、数据库记录、配置、Hook/MCP 客户端和扩展实现是否必须继续工作？迁移和回退策略是什么？
5. **平台差异**：macOS、Windows PowerShell 5.1/7、WSL、SSH 远端是否有不同的 stdin/stdout、信号、路径、PTY 尺寸或 quoting 行为？
6. **非目标**：本次明确不改什么？

计划中应列出可验证的验收条件，例如“关闭 Runtime 前必须经过桌面端确认”“旧字段缺失时按默认值读取”“远端命令不经过本地 shell 重新解析”，而不是只写“功能正常”。

## 3. 给 AI 的工作协议

L2/L3 按以下顺序工作：

1. 阅读 `AGENTS.md`、相关设计章节和相关代码；不要默认通读所有开发文档。先输出简短的影响面、数据归属、调用链和测试计划。
2. 用户已授权且目标与计划清楚时直接实施；缺少关键条件、授权或需要扩大范围时再询问。复用现有 manager、backend、contract、i18n 和平台 helper，不建立平行状态或第二套实现。
3. 每完成一个逻辑块就运行最小相关测试；不要把所有错误留到最后一次处理。
4. 不以“编译通过”作为完成标准。必须证明功能、边界、异常、兼容性和副作用都符合验收条件。
5. AI 不得自行扩大需求、删除既有测试、绕过确认机制、暴露凭据，或为了通过测试修改测试期望。

## 4. 实现约束

### 模块与依赖

- 前端通过稳定的 Tauri API/事件与原生层通信；不要从组件直接复制数据库或 Runtime 状态。
- Rust 模块保持单向依赖：command 负责边界转换，service/manager 负责业务编排，backend 负责 I/O，contract 负责跨进程数据形状。
- 新概念放入拥有其生命周期和数据的模块；禁止绕过 manager 访问内部集合，禁止为同一实体建立平行缓存。
- 修改公共 JSON、Runtime contract、Control contract、数据库字段或 MCP schema 时，必须同时更新生成/同步脚本、消费者和兼容测试。

### 跨平台与运行时

- 终端、PTY、Agent、Hook、MCP、浏览器、WSL 和 SSH 改动必须遵守 `AGENTS.md` 的跨平台要求，复用现有 target-specific helper。
- 生命周期改动必须说明启动、停止、异常退出、应用退出和重复调用的幂等性；重要副作用保留用户确认边界。
- 凭据、私钥、API Key 和原始 CDP 端口不得进入日志、MCP 返回值、事件 payload 或测试 fixture。

### 前端与本地化

- 组件使用稳定 i18n key，不内联中英文文案；新增词条同步所有 locale 并运行 `npm run i18n:check`。
- 共享 UI 状态只保留一个来源；事件订阅必须在卸载时清理，异步请求必须处理过期结果和错误状态。
- 界面遵循 `AGENTS.md` 中的桌面设计语言，复用现有样式和组件。
- 交互入口按当前状态展示；未连接时不提供依赖连接的工作视图。新增页面须检查键盘焦点、禁用状态、明暗主题和窄窗格布局。
- UI 修改不能只以类型检查通过作为验收；需操作实际组件检查主流程，并在工具可用时检查截图。截图不可用时明确记录原因，不将 DOM 或类型检查称作视觉验收。

## 5. 测试与证据矩阵

按实际风险从下表选择场景，不要求机械覆盖不相关项：

| 场景 | 证据 |
| --- | --- |
| 主流程 | 单元/组件测试或可重复的端到端步骤 |
| 边界与空值 | 明确输入、预期输出和错误类型 |
| 异常与取消 | 子进程、网络、权限、超时、重复调用、应用退出 |
| 兼容性 | 旧 JSON/配置/API/数据库记录的读取或迁移测试 |
| 架构 | 依赖方向、唯一数据归属、契约字段和 schema 检查 |
| 平台 | 受影响的 macOS、Windows、PowerShell、WSL、SSH 实机或明确记录未覆盖风险 |

验证范围按第 1 节的分级表执行。权限、协议和平台适配测试应使用实际客户端输入及目标环境的继承条件；具体字段、环境变量和复现步骤保留在对应回归测试中。

## 6. 按风险触发独立 Review

L3 必须使用没有实现过程记忆的新 AI 会话或人工审查者。L2 涉及公共契约、迁移、安全边界或并发行为时需要独立 Review；其余 L2 由实现者做针对性 diff Review。L0/L1 不要求独立 Review。

独立审查只提供需求、验收条件、变更 diff 和测试结果，并检查以下相关维度：

- 模块边界与依赖方向
- 数据归属、内聚性与耦合
- 旧 API/JSON/配置/扩展兼容性
- 改动局部性与可维护性
- 异常、并发、远端行为和可运维性
- 测试是否覆盖主流程、边界、异常和兼容场景

任何“可能”都要落成复现步骤、代码位置或缺失测试；没有证据不能标记为通过。修复 Review 发现的问题时重新检查 diff 范围，避免用无关重构掩盖风险。

## 7. PR 与合并门槛

L2/L3 的 PR 描述必须包含：修改边界、数据归属/调用链、兼容性与平台影响、测试结果、未覆盖风险，以及按第 6 节触发时的独立 Review 结论。L0/L1 只需说明改动与验证结果。以下任一项不满足则不合并：

- 验收条件无法逐条映射到实现或测试；
- `npm run check`、`npm test` 或对应高级别验证失败；
- 契约/迁移/本地化文件未同步；
- 跨平台风险未验证且未明确记录；
- 引入第二个事实来源、绕过安全确认或泄露敏感信息；
- diff 包含无法解释的无关重构。

## 8. 规范自身的维护

具体缺陷和审查发现优先落实为回归测试，不要求每次追加规范。只有长期协作原则或质量门槛确实变化时才修改本规范；设计文档只在产品范围、架构、职责或关键取舍变化时更新。

实现细节、测试参数和修复经过保留在代码、测试及提交说明中。发现文档与代码冲突时，先核对需求、契约和测试，确认哪一方过时，再修正；不把当前实现自动当作预期设计。
